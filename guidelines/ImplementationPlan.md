## 1. Audit of the existing codebase (baseline)

Measured on the repository as of 2026-09-27. All figures come from the actual tree, not from estimates.

### 1.1 Stack and build

- Single **Vite 6 + React 18 SPA** (`package.json` name: `@figma/my-make-file`), produced from a Figma Make export.
- `node_modules` is **not installed**, and there is **no git repository** initialised in the working tree.
- Entry chain: `index.html` → `src/main.tsx` → `src/app/App.tsx` → `src/app/routes.tsx` (`renderRoute()` switching over the `ViewState` union).
- **There is no URL routing.** Every page lives at `/`; navigation is in-memory `useState` (`useAppState` + `useAppNavigation`).
- Styling: **Tailwind CSS v4 via `@tailwindcss/vite`**; CSS entry `src/styles/index.css` (`@import 'tailwindcss' source(none)` + `@source '../../**/*.{js,ts,jsx,tsx}'`).
- Path alias `@` → `./src/app` (`vite.config.ts`).
- Custom Vite plugin `figmaAssetResolver()` maps `figma:asset/<hash>.png` → `src/assets/<hash>.png`.

### 1.2 Volume

| Metric | Value |
|---|---|
| Total TypeScript/TSX lines under `src/app` | ~81 955 |
| Components in `src/app/components` | 138 (including 48 shadcn/ui primitives) |
| Pages in `src/app/pages` | 22 |

### 1.3 Existing dashboards and their configuration

A single component, `UnifiedBusinessDashboard`, renders **all** business dashboards. It is driven by
`src/app/data/updatedBusinessDashboardConfigurations.ts` (consumed through the `useDashboardConfig` hook), with these keys:

`restaurants-fastfood` · `bars-maquis` · `metiers-bouche` · `epiceries` · `boutiques-superettes` (**currently aliased to `epiceries`**) · `fruiteries` · `producteurs-fournisseurs` · `catering`

`delivery`, `company` and `affiliate` are separate pages (`DeliveryDashboard.tsx`, `CompanyDashboard.tsx`, `AffiliateDashboard.tsx`).

Each configuration declares `ModuleConfig[]` (sidebar entries with submenus, an `isPremium` flag and a `priority`),
`MetricConfig[]` and `ActionConfig[]`. Shared modules (`commonBusinessModules`) already include
`pdv-caisse`, `comptabilite` (with `journal-ventes`, `factures-devis` …), `personnel-paie`, `infos-business`,
`parametres`, `config-site-web` and `marketing-avance`.

Already present and directly reusable: **`components/GenericSectionView.tsx`**, which renders any section id it does not
know about. This is the foundation for the requirement “dynamic page where no page is implemented”.

Routing of business sub-categories: `business-<sub-category>` user types are currently all routed to the legacy
`restaurant` dashboard regardless of the sub-category (see `useAppNavigation.handleLogin`), which is why the
`boutiques-superettes` configuration behaves as a duplicate of `epiceries` and why the merge requested in section B
is not merely cosmetic.

### 1.4 Authentication, data and content

- **Authentication is simulated.** `useAppNavigation.handleLogin` only sets `{ email, userType, isAuthenticated }`
  in memory: no API call, no token, no session persistence, no password verification.
- Demo accounts live in `src/app/utils/demoAccounts.ts` (`demo@restaurant.com`, …) and are documented as
  *to be deleted in production* in `src/app/DEMO_ACCOUNTS.md`.
- **All dashboard data is hardcoded mock data**: `src/app/data/mockOrdersData.ts`,
  `src/app/data/restaurantDashboardData.ts`, and inline arrays inside views (for example `pages/AdminDashboard.tsx`).
- A Supabase project reference exists (`src/app/utils/supabase/info.tsx`, autogenerated) together with a **Hono
  key-value stub** (`src/app/supabase/functions/server/kv_store.tsx`, table `kv_store_3b44d30c`). It is a KV store,
  **not a data layer**, and it backs none of the dashboards.
- `Header.tsx` and `Footer.tsx` are reusable components, but every page re-wires around fifteen callbacks.
  `TopBar.tsx` renders language and currency selectors that are **purely cosmetic** — there is no i18n library and no
  currency state anywhere.
- Public content (News, News detail, Vidéothèque, Use cases) is served from static arrays inside
  `pages/NewsPage.tsx` (695 lines) and `pages/VideoLibraryPage.tsx` (744 lines).

## 2. Validated technical decisions

Full reasoning, rejected alternatives and revisit triggers: `docs/adr/0001-architecture-decisions.md`.

| Topic | Decision | Why (short) |
|---|---|---|
| Backend | **NestJS 11** modular monolith with two entrypoints (`main.ts` = API, `worker.ts` = jobs) | Guards/interceptors give RBAC + tenant + premium enforcement declaratively; DI gives clean bounded contexts; built-in Swagger, WebSockets, BullMQ, scheduler; Jest matches TDD |
| Database | **PostgreSQL + Prisma on Neon** | Requested and validated; pooled URL for the app, direct URL for migrations; `prisma migrate` only, `db push` restricted to local dev |
| Multi-tenancy | **Shared schema**, `businessId` on every business-scoped table, **Postgres RLS**, Prisma `$extends` scoping, plus a Nest tenant guard | Defence in depth; cheapest to operate at this category count |
| Architecture style | **Modular monolith**, not microservices | A POS sale must atomically write order + stock movement + cash session + accounting entry + loyalty points; microservices would force sagas on the hottest path. The `worker` entrypoint provides the one split that is genuinely needed (integrations/reports scale separately) |
| Frontend topology | **One Next.js App Router app** (decision of 2026-09-27) with route groups `(marketing)`, `(auth)`, `admin`, `dashboard`, `(storefront)`. Implemented on **Next.js 16.3.6** in M0 — see the amendment to ADR-0001 §D4 | Satisfies the requirement (separate landing site, storefront, dashboards) while keeping one deployment and one CI pipeline; route groups isolate layouts and bundles without the operational cost of three apps |
| Monorepo tooling | **pnpm workspaces + Turborepo** | One lockfile; cached `lint/typecheck/test/build`; makes shared `packages/*` practical |
| Shared UI | `packages/ui` — shadcn/ui primitives, Chapfoody design tokens, Header, Footer, `DashboardShell` pieces | Requirement A.III (uniform header/footer) and B (shared shell, dashboards own their own components) |
| API contract | OpenAPI generated by `@nestjs/swagger` → typed client in `packages/api-client` | No hand-written DTO drift between the API and the frontend surfaces |
| Data fetching | TanStack Query (authenticated dashboards) + Next Server Components (public/SEO content) | Requirement B: no full reload, cached dashboard screens, ISR for marketing pages |
| i18n / currency | `next-intl` (FR default, EN available) + a cookie-persisted locale/currency state synced to the user profile when logged in | Requirement A.III: make the language and currency selectors functional |
| Auth | **Argon2id** password hashing, short-lived JWT access token, **httpOnly rotating refresh** cookie, **Google OAuth**, **TOTP MFA** | Requirements A.V and A.VI |
| Premium gating | `Feature` registry + `Entitlement` per business, enforced by a server-side `EntitlementGuard` | Requirement B: the client cannot reach CRUD of a feature its subscription does not allow |
| Testing | Jest + Supertest (api), Vitest + Testing Library (frontend), Playwright (E2E) | Requirement G: TDD architecture |
| Payments (storefront) | `PaymentProvider` abstraction — Stripe first, then CinetPay/Paystack/Flutterwave | Target-market reality in francophone Africa; the abstraction avoids a rewrite |
| Media | Object storage with signed uploads (S3-compatible / UploadThing) | Blog, Vidéothèque thumbnails, product images, theme assets |
| Observability | Sentry (frontend + API), OpenTelemetry traces, structured logs with request ids | Requirement G: security first, and operability of a multi-tenant platform |
| Deployment | Vercel (Next.js) + Fly/Render (NestJS api & worker) + Neon (Postgres) + Redis (Upstash) | Scale-to-zero friendly, minimal ops at prototype stage |

**Ownership and boundary rules**

1. A dashboard never imports from another dashboard. A cross-dashboard need goes to `features/_shared` or `packages/ui`.
2. Anything used by two or more dashboards is promoted to `_shared` in the same PR that introduces the second use.
3. `features/<dashboard>/` owns its `components/`, `api/`, `hooks/`, `nav-config.ts` and `types.ts`.
4. `nav-config.ts` is the single source of truth for that dashboard's sidebar (labels, icons, order, premium flags,
   route targets). The sidebar, the fallback page and the E2E navigation test all read from it.
5. `legacy/` is read-only and excluded from lint/CI. It stays buildable until M8 parity, then is archived to a tag.
6. Backend: a module exposes a service API and never lets another module import its repository or a Prisma model.

### 5.3 Multi-tenancy and database security

1. Every business-scoped table carries `businessId`, indexed, and included in every unique constraint
   (for example `@@unique([businessId, slug])`).
2. **Postgres RLS** is enabled on every business-scoped table, with a policy of the form
   `USING (business_id = current_setting('app.business_id', true)::uuid)`.
3. The API sets `app.business_id` per request inside the transaction (`SET LOCAL`), never outside it.
4. Prisma `$extends` injects the tenant filter automatically, so an unscoped query cannot be written by accident.
5. A Nest `TenantGuard` rejects any payload containing an id that does not belong to the caller's business.
6. `AuditLog` records actor, business, action, entity and a before/after hash for every write.
7. Cross-tenant access attempts are logged and surfaced to the super-admin.
8. Integration tokens are encrypted at rest with envelope encryption; the plaintext never reaches logs or the client.

**A CONSTRAINT FOUND WHILE WRITING THOSE TESTS, AND IT AFFECTS HOW THE COMMENT ENDPOINT MUST BE WRITTEN**

The public comment path **cannot use Prisma's `create`**. `create` issues `INSERT … RETURNING`, and PostgreSQL
subjects the RETURNING clause to the SELECT policy — and a PENDING comment is deliberately invisible to the public,
so the row it has just written is not visible to the writer either. The insert is refused outright. Verified by
experiment, not by reading the manual: the identical statement succeeds without RETURNING and fails with it.

This is the policy being coherent rather than a quirk to work around. An anonymous writer is not allowed to read
back what they wrote, so the public path must insert **without** asking for the row and the application must
generate the id itself — which is free, because Prisma's `@default(cuid())` runs client-side. Both halves are now
asserted in the suite, including the RETURNING refusal, so that a future policy change cannot silently reopen the
path while quietly breaking the moderation guarantee it was protecting.

The customers increment closed both loose ends that had been flagged for two increments:

  - `Order.customerId` is now a real foreign key. The free-text delivery fields on the order stay, and that is
    deliberate: they are the address the customer gave on the night, and a customer who moves house next month
    must not change where last month's order went.
  - `Referral.customerRef` (a free-text placeholder) is gone, replaced by a real `customerId`. The placeholder was
    honest about being one; the moment a constraint was possible it became one.

Two things were found by tests rather than by review, and both are now enforced in the database:

  1. **A tenant could file a row against another tenant's customer.** `customer_address`, `customer_note` and
     `customer_consent` pointed at `customer(id)` alone. Because the scoping layer rewrites `business_id` to the
     caller's context, tenant B could insert a consent event naming tenant A's customer and both the INSERT policy
     and the foreign key were satisfied. Nothing leaked — A never sees the row — but the reference was real, and
     any query joining on `customer_id` without also matching `business_id` would have followed it. The
     isolation suite attempted exactly that and was allowed to. Fixed by making the key composite:
     `(business_id, customer_id) → customer(business_id, id)`, which requires a redundant-looking
     `UNIQUE (business_id, id)` as its target. **The constraint, when applied, refused to be created until three
     real cross-tenant rows left behind by that test were removed** — the database found the bad data itself.
  2. **A seed that skips is a seed that does not converge.** Re-running after this increment left the demo orders
     with a null `customerId`, because the orders already existed and the seeder skipped them entirely. The
     reconciliation then computed zero orders for their customer and looked perfectly correct while being wrong.
     The same bug existed in the affiliate seed's new `customerId`. Both now fill a null and leave a deliberate
     non-null alone.

A related decision worth recording: **customers are anonymised, never deleted.** A customer can demand erasure,
but the accounting domain has to keep the sale for years and an order without a customer is a hole in the books.
`anonymizedAt` records that the PII was stripped and the history kept, and a CHECK refuses an anonymisation that
leaves an email, phone, surname, company name or account behind. A `DELETE` would satisfy one obligation by
breaking the other.

  1. **Prisma's interactive transaction timeout is 5 seconds**, and the seed hit it once enough domains existed —
     "a query cannot be executed on an expired transaction" at 5 364 ms. `runAsTenant` takes optional

     The raised limit has only been exercised against a WARM database, where most of the work is already done.
     **A cold CI database or a fresh Neon branch is where it will bite, and it has not been tested there.**

Four mechanisms now do work that would otherwise be re-derived per domain.

RLS reconciles itself — each domain migration ends with one line, which protects any table that has since appeared
with a `business_id` column and skips any that already has a policy. That is how the hand-written policies on
`audit_log`, `stock_movement`, `order_status_history`, `cash_movement` and `refund` survive:

```sql
SELECT cf_apply_tenant_rls();
```

The arithmetic the money depends on is asserted by the database rather than trusted:

```sql
round(subtotal - discount_amount + tax_amount + ... - rounding_amount, 2) = total  -- a receipt adds up
difference  = counted_cash - expected_cash                                          -- the drawer balances
net_tax_due = collected_tax - deductible_tax                                        -- the return reconciles
round(total_liabilities + total_equity, 2) = total_assets                           -- the sheet balances
```

Uniqueness a Prisma key cannot express is enforced by partial indexes: one open till per location, one default stock
location per business, one price per target per list, one default order type.

And a rule about two ROWS rather than one — enforced by an EXCLUDE constraint over a date range, which is the only
way SQL can say it. An employee's contracts may not cover the same day, so a permanent contract and a later
fixed-term amendment conflict instead of quietly coexisting and paying twice:

```sql
EXCLUDE USING gist ("employee_id" WITH =, daterange("start_date", COALESCE("end_date", 'infinity'), '[)') WITH &&)
```

And the one invariant no CHECK can express — that a journal entry's lines add up to its totals, and that it balances
— is enforced by a DEFERRABLE constraint trigger. Deferred matters: within a transaction the debit and credit lines
may be inserted in any order, and only the committed state is verified. The accounting policies go further than
tenancy: a posted entry cannot be updated, only reversed, and its lines can only be written while the parent entry
is still a draft.

*Configuration* (`src/config/env.ts` + `auth-env.spec.ts`, 35 tests). Signing secrets, token lifetimes,
cookie policy, lockout policy, MFA issuer and the Google OAuth settings are validated at boot. The rules
worth naming: production requires two **explicit, distinct, 32+ character** secrets (a development
default reaching production lets anybody mint a token for anybody, and the same secret in both variables
silently removes the reason the refresh hash is keyed); the refresh lifetime must **exceed** the access
lifetime (otherwise every session dies at the first refresh and it presents as intermittent logout);
`Secure` defaults from the environment, because forcing it on breaks localhost over http and the failure
looks like "login does nothing". `parseDurationSeconds` (9 tests) converts `15m`/`30d`, since `15m`
parsed as 15 *seconds* would lock everybody out.

*Tokens and sessions* (`src/modules/auth/token.service.ts` + 12 unit tests). Access token is a stateless
15-minute JWT; the refresh token is an **opaque 32-byte random string stored as a keyed HMAC-SHA256**,
matching the `VarChar(64)` the schema sized for it. Rotation revokes before reissuing, in one
transaction. **A replayed token revokes the whole family** — the signature of a stolen token, and a
deliberate trade against the case where a double-submitted request trips it. Expiry and explicit
revocation are *not* theft and leave the family alone, which is asserted, because getting that backwards
would sign a user's other devices out for no reason.

The data layer needed nothing: M2 already models `Session` (with revocation reasons), `RefreshToken`
(`tokenHash` + `familyId` + `replacedById` — exactly the shape reuse detection needs), `Account`,
`MfaSecret`, `RecoveryCode` and `VerificationToken`, and `User` carries `failedLoginAttempts` /
`lockedUntil`. `CURRENT_MILESTONE` moved from `M1` (stale since M2 landed) to `M3`.

**Still to do in M3** — password login and the `/auth/*` endpoints `[x]` (login, refresh, logout, me);
the four guards `[x]` (`JwtAuthGuard`, `TenantGuard`, `RolesGuard`, `EntitlementGuard` with
`@RequiresFeature`); lockout enforcement `[x]` (in login). Remaining: MFA TOTP enrolment and step-up,
Google OAuth with account linking, throttling (`@nestjs/throttler`), the audit interceptor, the email
service through BullMQ, and the session-listing endpoints.

**Four slices done, all tested.**

*Configuration* (35 tests) — secrets, lifetimes, cookie policy, lockout policy, MFA issuer, OAuth
settings, all validated at boot. `parseDurationSeconds` (9 tests) converts `15m`/`30d`, since `15m`
parsed as 15 *seconds* would lock everybody out.

*Tokens and sessions* (12 tests) — stateless 15-minute JWT access token; an OPAQUE 32-byte refresh token
stored as a keyed HMAC-SHA256. Rotation revokes before reissuing, in one transaction. **A replayed token
revokes the whole family**; expiry and explicit revocation are not theft and leave it alone, which is
asserted.

*Login and the `/auth/*` endpoints* (12 guard + 11 cookie tests) — every failure is the same 401 except
lockout; an unknown e-mail still spends a full Argon2id verify against a throwaway hash, because
otherwise response time is a free account-enumeration oracle; the account is re-checked on every refresh,
not only at login; the refresh token never appears in a response body; and the default business is read
through `runAsTenant`, without which every session would silently be scoped to no business at all.

*The four access guards* (11 tests) — registered globally in a fixed order (auth → tenant → role →
entitlement), because each depends on the previous one's work. `TenantGuard` resolves the membership once
and attaches it, so `RolesGuard` cannot disagree with it. `RolesGuard` exempts platform staff and
`EntitlementGuard` does not — a super-admin belongs to no tenant, but entitlement is about what a
business has paid for. Entitlement is checked against `Entitlement` rows rather than a plan name,
`expiresAt` is evaluated at check time so a lapsed trial closes itself, and an unknown feature key
refuses rather than allowing.

CommonJS, so it failed to import outright; pinned to v11, which is CJS and pairs with NestJS 11.

## 7. Engineering conventions

### 7.1 Naming

| Thing | Convention | Example |
|---|---|---|
| Routes | kebab-case, stable; UI labels stay French | `/dashboard/rapport-ventes/liste-des-ventes` |
| Feature folders | kebab-case, one per dashboard | `features/boutiques-supermarche/` |
| React components | PascalCase file and export, one component per file | `DashboardShell.tsx` |
| Hooks | `use*`, placed in the feature's `hooks/` | `useEntitlement.ts` |
| Prisma models | PascalCase singular | `PurchaseOrderLine` |
| Database columns | snake_case through `@map` | `business_id` |
| API endpoints | REST, plural nouns, versioned | `/v1/orders`, `/v1/orders/:id` |
| Domain events | past tense, `domain.entity.action` | `order.created`, `subscription.updated` |
| Query keys | `[domain, scope, params]` | `['orders', businessId, { status }]` |
| Premium features | one `Feature` registry, dotted keys | `marketing.campaigns`, `storefront.customDomain` |
| Feature flags | `feature.*` environment-scoped | `feature.payment.cinetpay` |

### 7.2 TDD rules

1. No feature code is merged without a test that first failed and then passed in the same PR.
2. Layers: unit tests for pure logic (pricing, VAT, commissions, entitlements, report aggregation); integration tests
   for every endpoint (happy path + tenant isolation + entitlement + validation failure); component tests for views;
   one E2E test per user journey.
3. Coverage gates: `apps/api` ≥ 80 % statements / 70 % branches; `apps/next` ≥ 70 % on `features/_shared` and on
   dashboard API layers; **100 % on money-related functions**.
4. CI order: lint → typecheck → unit → integration (Neon ephemeral branch) → build → E2E for PRs touching `dashboard`
   or `storefront`.
5. Fixtures are factories (`makeBusiness()`, `makeOrder()`, `makeProduct()`), never copy-pasted literals.

### 7.3 Security rules

1. **The server is the only source of truth** for permissions, entitlements and tenant scope. Client-side checks are
   user experience only.
2. Validate every input at the boundary (DTO + `class-validator`) and reject unknown fields
   (`forbidNonWhitelisted`).
3. Never ship secrets to the frontend; encrypt integration tokens at rest; never commit `.env`; CI greps the client
   bundle for known secret patterns.
4. Every write is audited: actor, tenant, entity, action and a diff hash in `AuditLog`.
5. Database roles follow least privilege — the application role is not a superuser, and RLS stays enabled on every
   business-scoped table.
6. Passwords use Argon2id with a policy and a breached-password check. MFA is available to everyone and mandatory for
   super-admin.
7. Rate-limit authentication, checkout, exports and integration webhooks.
8. File uploads validate MIME type and magic bytes, enforce size limits, are never executable, and pass through a
   virus-scan hook.
9. Dependency hygiene: Dependabot plus `pnpm audit` in CI, committed lockfile, no unpinned third-party scripts.
10. The threat model is updated whenever a new public endpoint or external integration is added.

### 7.4 Git, branching and review

- Trunk-based development: short-lived branches `feat/<area>-<subject>`, `fix/…`, `chore/…`, merged into `main` behind
  green CI.
- Conventional Commits (`feat(orders): …`, `fix(pos): …`), with a PR template that requires the requirement id from
  section 9.
- Every PR states the milestone and requirement it addresses, lists the tests added, and includes screenshots or a
  short recording for UI changes.
- Migrations are one-way artifacts: a PR adding a schema change includes its migration **and** a rollback note.
- No direct push to `main`; at least one review; CODEOWNERS on `prisma/`, `apps/api/src/modules/auth`,
  `features/*storefront*`, `features/*affilie*` and `packages/ui`.

## 8. Environments, secrets and CI/CD

| Environment | Frontend | API | Database | Purpose |
|---|---|---|---|---|
| Local | `next dev` | `nest start --watch` | Docker Postgres + Redis (Neon `dev` branch optional) | Development |
| Preview (per PR) | Vercel preview | Preview deployment | Neon branch per PR (ephemeral, auto-deleted) | Review and E2E |
| Staging | Vercel | Fly/Render staging | Neon `staging` branch, anonymised data | Pre-release validation |
| Production | Vercel (edge) | Fly/Render, two or more instances | Neon `main` branch with PITR | Live |

**Secrets**

- Stored in Vercel and the API provider's secret store; locally in `.env.local`, which is git-ignored.
- Rotation procedure documented in `docs/runbooks/`; no secret ever reaches the client bundle, verified by a CI grep.
- Seeded credentials exist only in `prisma/seed.ts` and are excluded from production images.

**CI (GitHub Actions), on every pull request**

```
install → lint → typecheck → unit tests → integration tests (Neon ephemeral branch)
        → build → E2E (Playwright) → migration check → deploy
```

**CD**

- Merge to `main` → automatic deployment to **staging**.
- Production requires a protected tag or manual approval; **migrations run before the application rollout**, each with
  a documented rollback plan.
- Preview environments are torn down automatically when the PR closes (including the Neon branch).

**Observability**

Sentry on both the frontend and the API, OpenTelemetry traces across API, worker and database, structured logs
carrying the request id, and alerts on error rate, p95 latency, queue depth and failed integration deliveries.
